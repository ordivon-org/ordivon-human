# Human High-Information Search — HF11 Action / Tool / Control Round 3

## 0. Starting question

HF20 Round 2 repeatedly routed its strongest calibration/control residual into HF11.

Round 3 therefore asks:

> Does HF11 contain a stable Human operational family around affordance calibration, tool-integrated control, online correction or execution fragility that HOC0–HOC10 do not already consume?

Possible outcomes remain equal:

```text
new Human operational family
cross-owner composition protocol
purpose-specific HF11 projection
neighboring system owner
no new generic owner
```

No HOC11 is presumed.

---

# 1. First structural correction: HF11 is not operationally thin in the HF21 sense

HF21 before HOC10 supplied ontology/distinctions but lacked a practical regulation-action grammar.

HF11 is different.

It already has an action pipeline:

```text
Action Goal / Selected Policy
→ Motor Preparation / Initiation
→ Control Policy / Motor Commands
→ Effector / Tool Movement
→ Online State Estimation + Correction
→ Task / Environmental Outcome
→ Reward / Consequence
```

and explicit distinctions for:

```text
feedforward control
feedback control
state estimation
online correction
prediction/task/reward error
motor adaptation
skill
affordance
attunement
calibration
tool control
tool integration
coordination
remote command
Human-machine control
```

So the methodological question becomes:

```text
Does practical consumption need a new HOC owner,
or only a canonical composition of HF11 with existing HOCs?
```

---

# 2. Candidate inventory

The highest-value candidate residuals are:

```text
A. AffordanceCalibrationCase
B. ToolIntegratedControlState
C. OnlineCorrection / ExecutionFragility
D. ControlArchitectureView
E. Human–Tool / Human–Agent Control Attribution
```

These are attacked separately.

---

# 3. Affordance calibration is real and practical

HF11 already separates:

```text
PhysicalActionPossibility
PerceivedAffordance
SelectedAction
```

and defines:

```text
Calibration_D
= scaling perception/action to the actual current relation between capability and
  environmental/task demand
```

with:

```text
Calibration != Capability
Attunement != Calibration
```

This matters operationally because:

```text
same Human
same goal
same nominal plan
same general skill
```

can fail when:

```text
body state changed
tool length changed
tool mapping changed
terrain changed
fatigue changed
assistive device changed
```

while the Human still acts from an outdated action boundary.

---

# 4. But affordance calibration does not leave a new HOC-level owner

A practical affordance-calibration case can be composed as:

```text
HF11
→ PhysicalActionPossibility
→ PerceivedAffordance
→ Calibration / Attunement
→ tool/body/environment relation

HOC1
→ current capability/support/readiness
→ fragile dependencies

HOC2
→ evidence for current action-boundary estimate if verification matters

HOC3
→ recalibration learning, retention and transfer

HOC5
→ selected action / execution mode / stop or retry

World
→ actual physical/environmental constraints
```

No additional generic Human state is required.

Thus retain:

```text
AffordanceCalibrationCase
= purpose-specific HF11 operational projection
```

not a new HOC family.

---

# 5. Calibration is task/information specific

Prior Human affordance research already showed recalibration may fail to transfer between functionally similar actions when their informational requirements differ.

That remains a strong guard:

```text
Calibration(TaskA)
!= Calibration(TaskB)
```

and:

```text
CalibratedToolUse
!= GeneralToolCalibration
```

This argues against one global `ActionCalibration` profile.

---

# 6. Modern motor adaptation strengthens context specificity

A 2025 visuomotor-adaptation study found that target configuration changed not only how Humans adapted but what representation they learned under the perturbation.

Different training geometries favored different mixtures of explicit/implicit adaptation and different learned mappings.

Operational consequence:

```text
SuccessfulAdaptationInTrainingContext
!= GenericCorrectInternalMapping
```

and:

```text
TrainingConfiguration
can change learned control representation.
```

This is already naturally represented by HF11 + HOC3 TransferSurface.

---

# 7. ToolIntegratedControl is not one Human property

HF11 already separates:

```text
ToolAvailability
ToolKnowledge
ToolSelection
ToolControlSkill
ToolControlIntegration
ToolEffect
```

and allows:

```text
Affordance(HumanToolSystem, E, T)
```

without treating the tool as biological/person identity.

Therefore the useful question is not:

```text
How integrated is this tool with the Human?
```

as one scalar.

It is:

```text
Which dimensions of control/capability/body representation/ownership are integrated,
for which task, under what support and feedback architecture?
```

---

HOC1 freezes:

```text
SituatedCapability

```

and explicitly handles:

```text

```

is already canonical.

This removes one of the strongest arguments for a new tool-integration HOC.

# 9. HOC3 owns learning / retention / transfer of tool control

If the practical question is:

```text

Will performance persist?

```

HOC3 already has:

```text
LearningTrajectory

SupportDependenceTrajectory

```

with `partner/tool change` explicitly included as a transfer dimension.

Therefore:

```text
OnlineJointPerformance
!= LearnedToolControl
```

and no new family is required for learning attribution.

---

# 10. HOC8 owns tool knowledge / procedural competence evidence

A Human can:

```text
know how a tool/controller works
explain it
select it appropriately
```

while still lacking smooth control integration.

That distinction is real:

```text
ToolKnowledge != ToolControlSkill
```

but HOC8 already owns knowledge/procedural competence claims while HF11/HOC1 own action/control capability.

No new owner emerges from the knowledge-control split.

---

# 11. HOC9 owns automaticity / contextual control after repeated tool use

Repeated tool use can become fluent/automatic/routinized.

But:

```text
ToolControlAutomaticity
!= ToolControlSkill
!= ToolIntegrationTotality
```

HOC9 already owns automaticity/context sensitivity.

Thus automatic control does not justify a separate HF11-derived family either.

---

# 12. Execution fragility initially appears stronger

Consider two Humans with similar endpoint task success:

```text
H1
→ smooth feedforward control
→ few corrections
→ low attentional burden

H2
→ repeated online corrections
→ high visual-feedback dependence
→ high cognitive/physical burden
→ still reaches same endpoint
```

If only final task success is recorded, these are falsely equated.

This suggests a possible object:

```text
ExecutionFragilityView
```

---

# 13. But HOC1 + HOC5 + HF11 already reconstruct fragility

HOC1 CapabilitySurface can include:

```text
error profile
variability
resource/effort cost
recovery after interruption/error
support dependence
```

and HOC1 explicitly recognizes:

```text
FRAGILE
CONDITIONALLY_RELIABLE
ROBUST
```

HOC5 ExecutionProfile adds:

```text
initiation reliability
continuation
interruption recovery
adaptive deviation
completion reliability
support dependence
stop/abandon quality
```

HF11 supplies the mechanism-side control architecture:

```text
feedforward dependence
feedback dependence
online state estimation
online correction
```

Thus a practical `ExecutionFragilityView` is a composition:

```text
HOC1 outcome/reliability/fragility
+ HOC5 execution trajectory
+ HF11 control architecture
```

not a new owner.

---

# 14. Online correction is consequential but already HF11-owned

Recent Human motor-control evidence continues to show that online correction materially changes performance and adaptation.

A 2026 reaching study comparing conditions with and without within-trial correction found lower angular errors and higher learning rates when online correction was available.

Another 2026 perturbation study found Humans combine anticipatory, robust and online-adaptive feedback strategies differently under predictable versus unpredictable dynamics.

Thus:

```text
SameEndpointGoal
+ different online-control architecture
→ different performance/adaptation profile
```

But this does not reveal a missing HOC because HF11 directly owns online correction/control architecture.

---

# 15. Feedback dependence is not failure by definition

A controller may rationally rely on online feedback when:

```text
environment is unpredictable
model uncertainty is high
perturbations are frequent
```

while greater feedforward dependence may be efficient in stable settings.

Therefore reject:

```text
MoreFeedforward = BetterSkill
MoreCorrection = WorseSkill
```

without context.

A fragility claim requires task/consequence/effort/recovery evidence.

---

# 16. Shared-control Human-machine systems are the strongest modern pressure case

Current assistive technologies make the attribution problem concrete.

A 2025 intelligent bionic-hand study continuously blended machine and Human control. Machine assistance conformed individual digits to the object while the user retained proportional grasp regulation; shared control improved dexterity and reduced cognitive burden relative to more purely Human-driven control under the study conditions.

Therefore:

```text
JointTaskPerformanceGain
can arise from
MachineControlContribution
```

without proving equivalent increase in Human independent manual control.

This is exactly HOC1 support attribution + HF11 control architecture.

---

# 17. Assistive robot shared control separates command from low-level realization

A 2025 assistive-robot study with people with severe motor impairment used sEMG commands, shared-control templates and whole-body coordination to execute sequences of everyday tasks.

The Human remained the task-level commander while the system guided/constrained task-relevant motion and automatically coordinated additional degrees of freedom.

This exposes at least:

```text
Human task goal/command
Machine task-space assistance
Machine low-level coordination
World/model constraints
```

in one successful action.

Thus:

```text
HumanCommand
!= HumanLowLevelControl
!= JointSystemExecution
```

and:

```text
TaskControlAuthority
!= MotorControlContribution
```

---

# 18. Online device adaptation further separates Human and tool/controller change

A 2025 exoskeleton study used online adaptation to update a user state-estimation model and reported improved gait-phase estimation and assistance timing after brief adaptation.

This is important because system performance can improve through:

```text
DeviceModelAdaptation
```

rather than:

```text
HumanLearning
```

or even:

```text
HumanControlImprovement.
```

Therefore retain:

```text
ControllerAdaptation
!= HumanAdaptation
```

and route Human-learning claims to HOC3.

---

# 19. Offline model accuracy can diverge from online control quality

A recent user-in-the-loop myoelectric-control study found a zero-shot adaptive scheme could achieve higher online throughput despite lower offline classification accuracy than the baseline screen-guided approach.

This gives a useful engineering/Human-control firewall:

```text
OfflineDecoderAccuracy
!= OnlineHumanToolControlQuality
```

and:

```text
ModelMetric
!= JointFunctionalPerformance
```

Again, this is an evaluation/attribution issue, not a missing Human family.

It is not a Human property.

# 23. Shared control is not one autonomy scalar

Shared control can operate through:

```text
policy blending
force-level assistance
user-input modulation
task-space constraints
automatic low-level coordination
intent inference
state-estimation adaptation
```

These mechanisms preserve different amounts/forms of Human control.

So:

```text
SharedControlLevel = 0.7
```

is usually too coarse without dimension/authority semantics.

# 26. Interface / Runtime / World ownership remains external

Human ontology must not absorb:

```text

servo stability
```

```text

```

HF11 can model their Human-action implications without becoming their engineering source of truth.
