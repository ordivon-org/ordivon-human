# CASE-001 — Student Builder with Strong Output but No Stable Market Exchange

**Status:** constructed on 2026-08-03; first evidence review pending.

## 0. Purpose and privacy boundary

This is a privacy-reduced reconstruction of a real current case. It is designed to test whether the practical E0–E9 path gives a feasible next action rather than an attractive life narrative.

The public version retains decision-relevant facts while removing or rounding:

- the exact university and city;
- exact account balances and family financial events;
- identifying project and provider details where unnecessary;
- names, contact information, and private records.

It is not individualized financial, legal, migration, or educational authority.

## 2. E0 diagnosis — the first unsupported transition

This case does not fit one clean stage.

| Transition | Current state |
|---|---|
| reliable learning and execution | partially supported |
| professional direction | provisionally supported |
| inspectable proof | strongly supported in volume, incompletely supported in independent capability and external legibility |
| trusted market exchange | not supported |
| recurring quality-preserving surplus | not supported independently |
| productive ownership | latent code and research ownership exists; productive demand is not supported |
| owner-independent system | not supported |
| capital-dominant autonomy | not supported |

The first important unsupported transition is:

```text
substantial self-directed technical output
→ one narrow result that an external party can understand, trust, use, and request again
```

The primary current bottleneck is therefore **E3: proof-to-market conversion**, not investment return and not the creation of additional broad projects.

A secondary bottleneck is **proof quality**: the current repositories demonstrate persistence and joint human–AI production, but they do not yet cleanly separate:

- independent technical understanding;
- model-produced implementation;
- actual user value;
- production reliability;
- the ability to work within another party’s constraints.

## 3. Current action ranking

The case model ranks the next uses of attention as follows:

1. preserve university access, health, and recoverability;
2. strengthen software and systems foundations enough to own the core work;
3. make one project capability legible to an external user;
4. complete a real responsibility-bearing or paid exchange;
5. improve English as a market and education access layer;
6. preserve small capital for continuity and options;
7. defer additional broad repositories, expensive educational commitments, and speculative optimisation until stronger evidence exists.

The ranking would change if a hidden fact showed that health, academic survival, family obligations, or immediate cash needs were already the binding constraint.

## 4. E1 — foundation education

### Strengths already visible

- unusually strong self-directed project persistence;
- comfort operating technical tools, repositories, Linux environments, deployments, and AI systems;
- ability to formulate systems questions and revise architecture;
- substantial written research and project documentation;
- willingness to delete work that no longer serves the problem.

### Foundation risks

- project breadth may conceal gaps in algorithms, data structures, operating systems, networking, databases, and software testing;
- AI agents may complete changes faster than the person can independently reconstruct them;
- multiple languages, tools, repositories, and research tracks may create recognition without depth;
- no current evidence establishes sustainable sleep, recovery, and weekly capacity;
- English may constrain access to documentation, interviews, collaborators, and postgraduate study.

### Thirty-day capability audit

Choose one technically central subsystem from the current project and complete all four tests:

1. **reconstruction test** — explain the subsystem from inputs to failure modes without opening the original implementation;
2. **modification test** — implement one bounded change and predict what tests or interfaces will break;
3. **debugging test** — resolve one failure without asking an AI agent for the complete solution;
4. **communication test** — write a concise English design note that another developer can inspect.

AI may be used afterward for critique and comparison. It should not erase the evidence the test is intended to produce.

### E1 evidence threshold

E1 is sufficiently strong for the next experiment when the person can:

- explain the chosen subsystem and its trade-offs;
- modify it under changed requirements;
- diagnose at least one failure from evidence;
- write tests or checks that distinguish success from appearance;
- identify which parts still depend on providers or agent output.

If this threshold fails, the correct move is to narrow the project and repair software foundations rather than add product features.

## 5. E2 — direction and professional choice

### Candidate path A — general software and systems engineering

**Advantages:** broad market transfer, strong foundation for infrastructure and AI work, clearer internship and employment proof.

**Risk:** may feel less distinctive than the current agent project and therefore receive insufficient attention.

### Candidate path B — agent infrastructure, reliability, and developer tools

**Advantages:** strong fit with the existing project; current industry work explicitly includes sandboxing, orchestration, stateful workflows, observability, reliability, execution environments, developer experience, and cost control.

**Risk:** many frontier roles are senior and require deep distributed-systems and production experience. The job title cannot be treated as an entry plan.

A current market check supports the existence of this problem family:

- OpenAI’s Agent Infrastructure and Codex Core Agents roles describe sandboxed execution, orchestration, state, tool use, reliability, latency, cost, and developer tooling;
- Anthropic lists infrastructure work in agent runtime, sandboxing, AI reliability, and developer productivity;
- Microsoft Research listed 2026 internships in AI Frontiers, Code|AI, self-improving AI, and agent efficiency.

These sources establish that the problem family exists. They do not establish that this student is currently competitive for those organizations.

### Candidate path C — immediate full-time founder

**Advantages:** maximum control over the project and high theoretical ownership.

**Risk:** no repeated external demand, no owner-independent system, small capital, and substantial educational opportunity cost.

**Current ranking:** reject as the primary 2026 path.

### Candidate path D — active trading as an economic path

**Advantages:** immediate feedback and theoretical upside.

**Risk:** prior repeated resets, no demonstrated durable edge, capital too small for return optimisation to dominate capability formation, and high attention cost.

**Current ranking:** reject as the primary economic path.

### Candidate path E — international postgraduate study

**Advantages:** language, credential, location, network, and market access may improve.

**Risk:** large family capital commitment may be made before professional direction, independent capability, and access value are sufficiently tested.

**Current ranking:** preserve as an access option, not as a substitute for market evidence.

### Provisional direction

```text
base capability:
software and systems engineering

specialisation test:
agent infrastructure, reliability, verification, and developer tools

access layer:
English, public technical communication, internships, and open-source collaboration

project role:
proof laboratory and possible ownership asset, not total personal identity
```

### Direction falsifiers

Reduce the specialisation and return to broader software foundations if:

- independent systems work remains weak after a focused repair cycle;
- external developers do not recognize the proposed problem;
- the project requires constant model orchestration but produces little transferable understanding;
- stronger evidence appears in another professional direction at lower cost.

## 6. E3 — proof and first market entry

### What the current project proves

It provides evidence of:

- sustained initiative;
- systems decomposition;
- repository and deployment operations;
- technical writing;
- iterative architecture;
- effective use of AI-assisted execution;
- willingness to maintain a long-running technical program.

### What it does not yet prove

It does not yet establish:

- that an outside user understands the value quickly;
- that another developer can install and use the system independently;
- that the owner can implement and debug the core without agent substitution;
- that the output changes an external decision or reduces a real cost;
- repeated demand;
- willingness to pay;
- team delivery under another party’s constraints.

### The first market wedge

Use one narrow capability already present in the project:

> Produce a reproducible evidence report for an AI coding-agent task: what changed, what commands ran, what tests passed, what artifacts remain, and what is still unknown.

The initial user is not a large enterprise. It is an independent developer or small project maintainer who already uses coding agents and has difficulty deciding whether an agent task can be trusted.

### Why this wedge is realistic

- it reuses existing runtime, artifact, verification, and recovery work;
- a manual report can be tested before a product is built;
- the value can be observed through a concrete decision;
- the first version can remain a script or documented workflow;
- failure still leaves technical documentation, tests, and user knowledge.

### Twelve-week experiment

#### Weeks 1–2 — problem contact

Speak with five developers who use coding agents. Ask for a recent task they found difficult to verify. Do not present a full platform first.

#### Weeks 3–4 — manual evidence reports

Produce three reports from the project’s own real tasks. Measure how long they take and which evidence is unavailable.

#### Weeks 5–6 — minimal reusable tool

Package only the repeated core required to generate a compact Markdown or JSON report from an existing repository and task record.

#### Weeks 7–9 — external runs

Support at least three external tasks. Observe installation, missing evidence, false confidence, and support burden.

#### Weeks 10–11 — revision

Remove unsupported claims, reduce setup, and document failure states.

#### Week 12 — next exchange

Ask for one stronger commitment: repeated use, a pilot, an integration, a contribution, a referral, or payment for a clearly bounded service.

### E3 evidence threshold

The experiment is strong enough to continue when it produces most of the following:

- five real problem conversations;
- three external task reports;
- two users who can operate the workflow with limited help;
- one repeated use or stronger commitment;
- one documented decision changed by the evidence;
- one external issue, contribution, or correction;
- a clearer statement of what the tool cannot prove.

### E3 stop rules

Stop or redesign when:

- ten relevant developers cannot describe the problem in concrete terms;
- users will not provide any task evidence even under appropriate privacy boundaries;
- setup and support exceed the decision value;
- the report repeats information already available more cheaply;
- the tool implies trust that the underlying evidence cannot justify.

## 7. E4 — early career and independent surplus

Family support currently creates valuable option space. It should be used to accelerate a credible transition, not to postpone external contact indefinitely.

### Near-term income routes

#### Route A — general tutoring or unrelated part-time work

This can produce immediate independently controlled cash and work discipline.

Its limitation is that it may consume prime learning time while adding little proof for the chosen technical direction.

Use only when:

- independent cash is a current need;
- hours remain bounded;
- the work does not displace the E1–E3 transition;
- the income funds continuity or a defined option.

#### Route B — technical internship, project responsibility, or bounded service

This is harder to obtain but produces aligned proof, access, and potential recurring income.

The current model ranks this route above maximizing unrelated part-time income when basic life is already supported.

### First independent-income objective

The first objective is not a target salary. It is one repeated external exchange connected to the chosen capability, such as:

- an internship responsibility;
- a paid technical audit or setup;
- a small recurring service;
- a research or engineering assistant task;
- a contribution that leads to a role or referral.

### Twelve-month transition evidence

The case should aim to establish at least one of:

- a substantive technical internship;
- repeated paid technical work;
- an open-source role with real responsibility and external references;
- a narrow owned product or service with repeated external use.

Without one of these, the project remains primarily private capability formation.

## 8. E5 — life quality and commitment control

### Current risk

The case has many high-intensity paths but no established weekly capacity. The main danger is not ordinary leisure spending. It is attention fragmentation and future commitments made before evidence.

### Four-week resource audit

Record only five functions:

1. essential life and university;
2. health, sleep, restoration, and relationships;
3. CS and English capability;
4. market proof and project production;
5. financial-market attention and low-value fragmentation.

The audit should identify one category that is materially crowding out the first unsupported transition.

### Commitment boundaries

- do not add a major tuition, relocation, debt, or business commitment before the access mechanism and family downside are explicit;
- do not maintain multiple paid tools or model subscriptions without current use in the primary path;
- do not let public project obligations make university, sleep, or health unrecoverable;
- do not convert temporary family support into permanent lifestyle commitments;
- do not treat constant market monitoring as necessary economic education.

### Postgraduate decision gate

A major postgraduate commitment should require:

- a verified English baseline and realistic improvement path;
- a clear target role or research direction;
- evidence that the selected program improves access to that path;
- full tuition, living, currency, and opportunity cost;
- the family’s safe loss capacity rather than nominal ability to pay;
- comparison with lower-cost routes such as transfer, internship, open source, or direct employment.

## 9. E6 — labour to ownership

### Existing ownership surfaces

The case already controls some potentially durable assets:

- original code and architecture where rights are clear;
- research notes and technical explanations;
- a project name and public history;
- deployment knowledge and operational procedures;
- a domain and direct publication surface;
- accumulated problem knowledge.

These are **latent ownership**, not yet productive ownership. Their economic value has not been established by external use or residual income.

### Practical ownership transition

The verification wedge should produce one reusable core:

```text
real agent task
→ collected execution evidence
→ normalized evidence model
→ compact report
→ user decision
```

The owner should preserve:

- a clear licence;
- exportable records and reports;
- local execution where feasible;
- direct documentation and contact surfaces;
- separation between provider-specific adapters and the core evidence model;
- explicit boundaries on what the report can prove.

### Ownership stop rule

Do not create another repository, platform layer, dashboard, or broad product surface unless external use reveals a requirement the current narrow artifact cannot satisfy.

## 10. E7 — ownership to system

The first system milestone is not revenue scale. It is one normal workflow that works without continuous owner rescue.

### Owner-absence test

A new developer should be able to:

1. understand the claimed result from the public description;
2. install or run the minimal workflow from documentation;
3. produce a report on a bounded task;
4. recognize an unknown or failure state;
5. file a useful issue without live owner interpretation.

### Scaling gates

Do not add staff, paid acquisition, major cloud expense, or complex governance until:

- repeat demand exists;
- the normal path is documented;
- support time per task is falling;
- one user has returned;
- the core can operate across more than one provider or task source where that matters;
- false confidence is bounded;
- a second person can handle at least one normal operation.

### What would count as system evidence

- three independent successful installations or uses;
- one repeated user;
- one external contribution or issue resolved through documentation;
- a bounded owner-absence period;
- evidence that the report reduces verification time or changes a release decision;
- support and maintenance lower than the value created.

## 11. E8 — capital by function

The case does not have enough verified information for product-level allocation or universal percentages.

The functional ranking is still clear.

### Continuity capital

Preserve immediately usable resources for:

- essential personal needs not covered at the moment they arise;
- replacement or repair of critical study and work equipment;
- examination, interview, or travel costs tied to a verified opportunity;
- the ability to avoid a forced financial decision.

### Option capital

Potential high-value uses include:

- English examinations after practice evidence is stable;
- a verified transfer or application cost;
- interviews and relocation exploration;
- core CS learning resources where free alternatives are insufficient;
- a bounded external-user experiment.

### Controlled productive capital

Only small staged spending is justified for:

- hosting or tools required by real external tests;
- a domain or distribution surface already used;
- an experiment whose next evidence is defined.

### Diversified productive claims

A small low-maintenance exposure may preserve the habit of long-horizon ownership, but it should not consume the attention needed for capability and market conversion.

### Speculative exposure

Because repeated reset-like losses already occurred and no durable edge is demonstrated, the case model ranks **no new speculative capital during the initial 90-day experiment** above continued trading.

Reopening would require a separate pre-registered research question, a loss boundary that cannot affect continuity or education, and evidence strong enough to justify the attention cost. Recovering prior losses is not an admissible objective.

### Minimum viable weekly rhythm

Outside compulsory university work, a twelve-hour weekly test is more credible than an open-ended high-intensity plan:

- three 90-minute software-foundation blocks;
- two two-hour wedge-building blocks;
- five 30-minute English blocks;
- one one-hour external-contact and review block;
- protected sleep, meals, movement, and recovery defined by the person.

This is a starting hypothesis, not an obligation or maximum. Increase effort only after several stable weeks; reduce scope immediately if university performance or functioning declines.

### Ninety-day evidence table

| Outcome | Evidence by 2026-11-01 |
|---|---|
| retained capability | one core subsystem independently explained, modified, debugged, and tested |
| external problem | five conversations and a stable problem statement, or explicit rejection |
| external use | three external tasks and at least two limited-help users |
| stronger exchange | one repeat use, pilot, contribution, referral, responsibility, or payment |
| access | concise English project explanation, technical résumé, and targeted external contacts |
| continuity | no new speculative reset; essential capital and university access preserved |
| life quality | no sustained degradation in sleep, health, or compulsory study attributable to the experiment |
| ownership | one reusable evidence model or workflow with controlled rights and explicit limits |

### Decision rules

**Scale** when independent capability and external repeated use both strengthen.

**Redesign** when the problem is real but setup, scope, or report quality prevents use.

**Return to foundations** when external interest exists but the person cannot safely own and modify the core.

**Stop** when relevant users do not recognize the problem, support exceeds value, or the evidence cannot justify the trust claim.

**Continue without expansion** when the current path works but no new evidence supports more complexity.

## 13. Competing paths rejected for the initial experiment

### Expand the entire project portfolio

Rejected because additional breadth weakens external legibility and does not test the missing market transition.

### Become a full-time founder now

Rejected because demand, repeatability, owner independence, and independent continuity capital are absent.

### Optimize financial returns

Rejected because the capital base is small, prior behaviour shows reset risk, and capability-to-market conversion has much larger plausible absolute effect.

### Commit to expensive postgraduate study immediately

Deferred because the education-access mechanism, English evidence, target role, and family downside are not yet complete.

### Maximize unrelated part-time income

Not rejected categorically. It remains a continuity option, but it should not consume the strongest hours while basic life is already supported and the primary market transition remains untested.

## 14. Model pressure points exposed by the case

### Mixed states are normal

The person has unusually large project output but remains economically dependent. A single stage label would hide this. The “first unsupported transition” method performs better than a total-stage classification.

### AI-assisted output weakens naive proof

Repository size and implementation speed can overstate retained capability. Proof must separate:

- human understanding;
- model contribution;
- joint output;
- external usefulness;
- controlled ownership.

### Family support has two effects

It increases option value and protects experimentation, but it can also delay external exchange and conceal whether the path is independently viable.

### Ownership can exist without production

Code and research may be legally controlled yet economically inactive. The case supports the distinction between latent ownership and productive ownership.

### Attention failure can dominate financial loss

Speculative activity damages not only capital but also the scarce attention needed for foundation, proof, English, and external contact.

## 15. Initial model verdict

The practical E-series currently ranks this case coherently:

```text
narrow external proof and retained capability
>
additional broad research or project expansion
>
small-capital return optimisation
```

No E-series revision is yet justified. The case does, however, create one explicit validation question:

> Can the proof-to-market protocol produce a real external exchange without requiring the person to abandon university, overstate AI-assisted capability, or build another large platform?

The answer must come from the 30-, 60-, and 90-day evidence reviews.
